what rig is

rig is a lean agent runtime — a minimal agent-loop machine, built closed. You talk, the model thinks, the tools do the work in your tree. Every dependency held at a typed seam, every induced work bounded, and the loop names no concrete type. Not a framework: a machine for one thing.

   assemble ─► stream ─► execute ─► feed back
      ▲                                     │
      └─────────────────────────────────────┘

one turn, faithfully — fault-aware, cancel-aware, and exactly once. the same machine runs your repl, your -p one-shots, and the scheduled workers.

three doors in. no sudo, no framework, no build step — pick one:

installer POSIX sh · checksums verified before anything moves · lands in ~/.local/bin · linux and darwin, amd64 and arm64 
❯ curl -fsSL https://mrsirg97-rgb.github.io/rig/install.sh | sh
release binary the same asset the installer fetches — pick rig_<os>_<arch>, the version lives in the URL 
❯ curl -fsSL https://github.com/mrsirg97-rgb/rig/releases/latest/download/rig_linux_amd64 -o rig
❯ chmod +x rig && ./rig --version
go install needs Go ≥ 1.26 — the core is stdlib-only; the one leaf is a pure-Go sqlite driver 
❯ go install github.com/mrsirg97-rgb/rig/cmd/rig@latest
then talk any OpenAI-compatible endpoint — a local server, a gateway, a hosted API. the wire protocol only. 
❯ rig --base-url $ENDPOINT --model $NAME

ten native tools, each a leaf behind the Tool seam — every call observed by the walls, bounded, and named.

  • bash — real subprocesses; output surfaced and bounded
  • file — read · write · edit; edits drift-checked against what you read
  • fs — ls · find · grep; small schemas a local model can reach
  • diff — the working tree vs HEAD, or the last observation of the same call
  • python — a persistent IPython kernel; state persists across calls
  • web — search via SearXNG; fetch with the SSRF guard and extraction
  • todo — the task queue; event-sourced, DAG-validated at create
  • rem — memory; recall by intent, consolidation arithmetic
  • scheduler — background jobs on cron; the worker runs in a bwrap jail
  • plugins_reload — re-discover from disk; the swap takes effect next turn

frontends — tui (the terminal default) · cli (the piped reference) · oneshot (-p, the worker)

one file under ~/.rig/plugins/ is one tool. the name is the filename, the description and schema are the file's, and the call rides the shared python kernel. loaded tools register on the same seam as the native set — indistinguishable on the wire. a broken file names itself and is skipped; it never bricks the harness.

# ~/.rig/plugins/uptime.py   →   the tool "uptime"
DESCRIPTION = "report host uptime, terse"
SCHEMA = {"type": "object", "properties": {}}

def run(args: dict) -> str:
    s = open("/proc/uptime").read().split()[0]
    return f"up {int(float(s) // 3600)}h {int(float(s) // 60) % 60:02d}m"

The design test, enforced structurally: adding a tool, a provider, a context policy, a frontend, or a tool middleware is one file plus one registration line at the composition root — the loop never names a concrete type.

why rig

▀▀▀ █▀█ ▀▀▀   █▀▄ █   █ █
█▀█ ▀ ▀  █    ▀ ▀ ▀   ▀▀▀
  • not a framework

    one machine, one job — the turn. assemble, stream, execute, feed back, repeat; exactly once, faithfully, against the seams you wire in.

  • built closed

    stdlib-only core; the one leaf is a pure-Go sqlite driver, justified in the spec. every dependency held at a typed seam, wired once at the composition root, swapped at registration with zero consumer changes.

  • the walls speak

    an allowlist (deny by default), a retry guard (the bound is named), an approval gate, a plugin landing zone. a refusal names the wall — and is final for that call.

  • fail closed

    a corrupt store is quarantined; a broken plugin is skipped by name; an unknown model row is loud, with the known set. uncertain state is a refusal, not a guess.

  • the log is the spine

    sessions outlive the process; the event log is the audit, and the queue and its projections are disposable — rebuilt in one transaction.

  • this page, on the same terms

    one file, zero requests after load, no framework, no build step, no webfont. readable with JS off — because seams should be swappable, never load-bearing.
