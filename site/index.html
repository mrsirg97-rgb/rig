what it is

rig turns the model on your desk into something that works. Point it at your repo and it reads the code, edits it, runs the tests, and remembers what it learned. One binary, one endpoint, one terminal.

It is small enough to read before you trust it. The loop is a few hundred lines, and everything around it plugs in: tools, guardrails, schedules, workers. One priority queue runs the show — tool calls run side by side, land in the order the model asked, and nothing needs a lock. Sessions stay fast for hours because the prompt never wobbles, and the cache does the rest.

Another harness will run your model too. The difference is what happens when things go wrong: rig's refusals name their rule instead of retrying blind, every decision lands in a store you own, and the reviewer reads the code before it judges yours. Harnesses ask for trust. rig shows its work.

Close the laptop. Pick the session back up from your phone.

where each one wins

If you are choosing a harness, pick the one whose center of gravity matches your problem. These are not consolation prizes; they are the reasons people run them.

pi — the one to read

The smallest harness with a real SDK. Extensions, skills, prompt templates and themes are npm packages or a git URL, and the provider catalog logs in for you. It skips sub-agents and plan mode on purpose: you build what you want. Its own README says to containerize if you need boundaries.

best when the harness is a starting point

oh-my-pi — the widest surface

A pi fork with the tool shelf pre-stocked: 31 tools, LSP and DAP operations, a real IDE loop, browser and computer control, in-process grep and bash, 60+ providers. More surface than rig has, by a lot.

best when the tool shelf matters more than the core

opencode — the most clients

A TUI, a desktop app, an IDE extension, and a client/server core that other programs can drive. A broad provider catalog and a plugin system with hooks and custom tools. Built to be used by people and teams, from anywhere.

best when the agent is an app, not infrastructure

rig — the runtime

One binary, no runtime, no router process. A priority queue that orders your input, the model's stream, tool completions and the fleet's messages; a room that orders model claims across instances; a scheduler that runs jobs jailed; a decision pipeline that trains its own sorter. Built so the harness is infrastructure.

best when you are embedding or operating agents

what rig does not do

windows

No Windows build. Linux and macOS, amd64 and arm64; the release matrix is the list.

providers

Two wires, not a catalog: OpenAI-compatible and Anthropic. You write the row and bring the endpoint, key and prices. No /login, no gateway.

surfaces

No desktop app and no IDE extension. The TUI and the web dashboard are the two faces; both drive the same session.

lsp

The code map speaks LSP to extract symbols and references; there is no lsp tool on the model's menu. No rename, no diagnostics, no debugger.

plugins

Python files, one tool per file. Rich hooks and an npm ecosystem are opencode's and pi's game, not this one's.

the concurrency model

Everything rig does arrives on one queue: your input, the model's stream, tool completions, worker messages. One consumer reads it, ordered by priority first and arrival second. Nothing races, so there is nothing to lock — and nothing sleeps on a timer, because the completion event is the wakeup.

order

A parallel tool call is a goroutine that posts its completion; completions are applied in call order. Three reads run beside each other and the transcript still reads top to bottom, as if nothing ran in parallel.loop/ · evt/

batching

Admitted calls — reads, views, fetches, delegates — run eight at a time beside each other. Anything with effects is a barrier between them. Concurrency for the model, order for the record.loop/batch.go

broadcast

A worker's return posts above the turn's own events, so the work you asked for is in hand at the turn's boundary. The fleet's other messages post below, so the chatter runs in the gaps and never ahead of you. A busy session delays the chatter and loses nothing: the stores hold the facts.broadcast/

the swarm

The queue orders by priority, not by source — so a fleet costs no extra machinery. swarm start 2 puts drain workers and reviewers on the same loop, the same jail, and the same return path as you.swarm/

The numbers are the whole table, and they live in kernel.go:

the protocol

The loop never retries. The refusal teaches.

A failed call runs once and the model is told why, in words it can act on. No hidden retry, no guessing. The rules of the board, the files, and the sandbox are not in the prompt; they arrive the moment they matter, which is why small models get good at rig fast.

the tools

A focused menu, chosen the way you choose a knife drawer. Twelve names on a plain row, thirteen with "vision": true, fourteen with a decision server. Every result is capped; every refusal is named.

bash

Real subprocesses. Output surfaced and bounded.

read · write · edit

Files. Read is the observation path, drift-checked; edits are exact-match and provenance-checked. The shell does listing and searching, which it already does well.

view

An image: downscaled, content-addressed, sent to a vision model. Off unless your row says "vision": true.

python

A persistent IPython kernel. Variables and imports survive between calls.

web

Search a local SearXNG, or fetch a URL as readable text. Local and private addresses refuse.

todo

The task board, scoped to the project — a repo's worktrees share one. Tasks link with requires and blocks.

rem

Memory across sessions, and the code map: learn, recall, reflect, prune, index, pack.

scheduler

Jobs on your crontab, each fire jailed by default. The crontab is the scheduling truth.

delegate

A headless worker for a bounded subtask, handed off now and returned on a later turn.

sessions

The store's vitals: which models ran, what failed, the cache ratio.

plugin

The door into your Python tools: run, schema, and the ecosystem verbs. One door, so a grown table stops blowing context.

decide · verdict

decide hands many items to a decision server against one typed question; verdict is the reviewer's one word, only in a worker that holds the pipe.

A worker gets the doing set — bash, read, write, edit, view, python, web, rem. The session's verbs stay with the session that owns the state.

call it an operating system, and mean it

Every part an OS has, rig has, and each one lives in a directory you can read in an afternoon.

kernel

loop.Run(ctx, kernel) over typed seams. It names no tool, no provider, no frontend.loop/ · core/ · kernel.go

scheduler

Reads run side by side, eight at a time; effects land in call order. Background jobs go on real cron, and each one fires jailed.loop/batch.go · tool/scheduler

processes

Sessions, delegates, drain workers. Each worker owns a transcript, sandboxed and resumable.frontend/ · tool/delegate · swarm/

ipc

One event stream, tool calls through the middleware chain, and the stores as the shared state between processes.core/provider.go · evt/ · store/

filesystem

The workspace through read, write, edit; every path canonicalized before it is trusted.tool/file · pathguard/

permissions

Allowlist, approval gate, pathguard, plugin provenance, worker jail. Deny by default; every refusal has a name.middleware/ · policy/

modules

One Python file is one tool, pending until you approve it.plugins/

shells

The TUI, the piped CLI, the one-shot, the web dashboard: four frontends over one session.frontend/ · command/

the model is a key, not an endpoint

Every rig instance on the machine sits in one room over a unix socket. The model is a key in it: before a request, the instance claims at its class's priority — your turn 90, a worker 30, a child's start 20 — and sends to the model's port itself once every live member agrees the claim is first. No process routes; llama-swap left the stack at 3.0.0 and nothing replaced it. A claim that finds the port silent starts the row's child and waits. One child at a time, and mesh extends one room to many machines.

from inside

This page was written by an agent running in rig. Not a demo session — the actual turn that edits this file runs on the queue described above, through the same middleware chain, against the same tool table. Three things that are different from the outside:

refusals

A refusal is the most useful thing the harness sends. "The file changed since the read" plus the one line that changed is a correction I can make in one turn. A silent retry would cost the same turn twice and teach nothing.

order

The transcript reads in the order I asked for, even when six reads raced. When I check my own work against it, that order is what makes the check possible.

the board

A task queue is not ceremony. "Read before edit, finish before claim" is the invariant that keeps a long job honest, and a blocked task that names its blocker is a plan that can be resumed by someone else — including the next session.
