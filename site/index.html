what it is

rig turns the model on your desk into something that works. Point it at your repo and it reads the code, edits it, runs the tests, and remembers what it learned. One binary, one endpoint, one terminal.

It is small enough to read before you trust it. The loop is a few hundred lines, and everything around it plugs in: tools, guardrails, schedules, workers. Tool calls run concurrently, sessions stay fast for hours because the prompt never wobbles, and the cache does the rest.

Close the laptop. Pick the session back up from your phone.

provenance

Built by hand until it could finish one turn. Everything after that, rig wrote inside itself, on local models, driven from a phone.

{{RIG_COMMITS}} commits · the git log is the receipt

the spec sheet

Call it a small operating system for agents and mean it. Every part an OS has, rig has, and each one lives in a directory you can read in an afternoon.

kernel

loop.Run(ctx, kernel) over typed seams. It names no tool, no provider, no frontend.loop/ · core/ · kernel.go

scheduler

Reads run side by side, eight at a time; effects land in call order. Background jobs go on real cron, and each one fires jailed.loop/batch.go · tool/scheduler

processes

Sessions, delegates, drain workers. Each worker owns a transcript, sandboxed and resumable.frontend/ · tool/delegate · swarm/

ipc

One event stream, tool calls through the middleware chain, and the stores as the shared state between processes.core/provider.go · evt/ · store/

filesystem

The workspace through read, write, edit; every path canonicalized before it is trusted.tool/file · pathguard/

permissions

Allowlist, approval gate, pathguard, plugin provenance, worker jail. Deny by default; every refusal has a name.middleware/ · policy/

modules

One Python file is one tool, pending until you approve it.plugins/

shells

The TUI, the piped CLI, the one-shot, the web dashboard: four frontends over one session.frontend/ · command/

the protocol

The loop never retries. The refusal teaches.

A failed call runs once and the model is told why, in words it can act on. No hidden retry, no guessing. The rules of the board, the files, and the sandbox are not in the prompt; they arrive the moment they matter, which is why small models get good at rig fast.

3

Make it yours

Two optional files. A theme is a base plus the colours you want to change. AGENTS.md in the rig home is your standing instructions, read before every session, ahead of the project's own.

~/.rig/theme.json

{
  "base": "warm",
  "slots": {
    "ember": "#6b7fa3",
    "text": "#b8bfcc",
    "dim": "#3a4150"
  }
}

~/.rig/AGENTS.md

# how I like to work
- run the tests before you say something is done
- prefer small commits with one idea each
- never add a dependency without saying why

4

Run it in a repo

The terminal opens. Ask for something real. Tool calls run in parallel and results land in order, so three reads cost one round trip and the transcript still reads top to bottom. Rig ships a carefully chosen, focused toolset: bash, read, write, edit, python, web, memory, todo, scheduler, workers. Reading is one tool, on purpose: every edit is checked against what the model actually read, and the shell does the listing and searching it already does well.

cd your-project && rig

6

Add a tool in one file

A plugin is a Python file: a description, a schema, and a run function. Drop it in and it shows up beside the built-in tools on the next turn. The model can write one too; it lands in a pending folder until you approve it.

~/.rig/plugins/weather.py

DESCRIPTION = "current weather for a city"
SCHEMA = {"type": "object", "properties": {"city": {"type": "string"}}}

def run(args):
    return fetch_weather(args["city"])

7

Organize the work

Tasks live on a board in the repo, with requires and blocks links between them. The model claims, works, and completes; you accept or reject. Add workers and they drain the same board.
