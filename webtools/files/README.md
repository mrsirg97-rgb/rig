# The rig web-tools bundle

Generated by `rig webtools setup` (rig {{VERSION}}). This is the bundle rig's
`web` tool talks to: SearXNG for search, its valkey for the limiter's bans, and
a tinyproxy that carries fetch's egress. Every file here is regenerated by
`rig webtools setup` except the two per-machine values: the `BasicAuth` password
in `tinyproxy/tinyproxy.conf` and `secret_key` in `searxng/settings.yml`, which
setup keeps once they exist.

- searxng answers on `127.0.0.1:{{SEARX_PORT}}` (rig's search default);
  tinyproxy on `127.0.0.1:{{PROXY_PORT}}` (rig's fetch default, BasicAuth
  `rig`/the password in the conf, realm `proxy`);
  valkey holds the limiter's pass-lists and is not published to the host.
- **Apply a conf edit with `docker compose up -d --build` in this directory, or
  `rig webtools start`.** The proxy's conf and deny-list are baked into its image
  by `tinyproxy/Dockerfile`, so a plain restart or `--force-recreate` keeps the
  copy already in the image. The searxng files are bind-mounted, so
  `docker compose restart searxng` does apply an edit to `settings.yml` or
  `limiter.toml`. Two services, two update paths.
- `rig webtools status` reports what is here against what rig generates, the
  daemon state, and `webFetchProxy` redacted. `setup` refuses to overwrite a file
  it did not write; `force` moves them, and names each one.
- The password is also in `~/.rig/settings.json` as
  `http://rig:<pw>@127.0.0.1:{{PROXY_PORT}}`. Rotate it by editing the
  `BasicAuth` line and that key together, then `up -d --build`. Both files are
  0600. Setting `webFetchProxy` to `""` makes fetch go direct (search is
  unaffected; it talks to searxng without a proxy).
- Hardening, as measured on 2026-10-26: `read_only`, `no-new-privileges`, memory
  and CPU caps with swap disabled, log rotation, non-root users
  (searxng `977:977`, valkey `999:1000`, tinyproxy `100`), the searxng limiter
  pass-listed only for the bridge gateway `{{GATEWAY}}` of `{{SUBNET}}` so
  host-originated searches are counted and relayed container traffic is not, and
  `tinyproxy/filter` refusing loopback, RFC1918, link-local (including
  `169.254.169.254`), `localhost` and `*.docker.internal` as fetch destinations.
- What the deny-list does not do, measured: it matches strings, so DNS rebinding
  slips; a `CONNECT` line can never match a `://` rule, so `ConnectPort 443` is
  what confines tunnels; and a first-label rule blocks every hostname that starts
  with that prefix (`10.9x.example.com` and `10.abc.example.com` are both
  refused), because the rule anchors on the prefix, not on an octet boundary.
- `tinyproxy` is pinned to Alpine's `1.11.3-r0` — the only build Alpine 3.23
  ships. CVE-2026-54387, CVE-2026-54388 (request smuggling) and CVE-2026-55202
  reach through 1.11.3, with no patched Alpine build yet; here the smuggling pair
  needs a client already inside the `Allow` line and past BasicAuth, and
  `EnableStats`/`Stathost`/`TransparentProxy` are not set. Watch for a `-r1`
  backport and bump the pin when it lands.
